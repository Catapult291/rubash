# 1.5.0 — workspace split, embeddable engine API, and the host boundary

Status: RFC draft v1 (2026-10-18) — awaiting owner sign-off on the shape and
the decision list in §8. Supersedes the sketch in #595 comments; builds on
#570 (boundary invariants), #593/#314 (driver API), #606 (usage lib),
#746 (regression ratchet), #729/#728 (carrier audit).

## 1. North star

1.5.0 cuts rubash from "a product" into **an embeddable GNU-bash-compatible
engine**, and demotes niubash to its first full consumer. The acceptance
criterion for the whole release: an external editor (oh-my-pi, Zed) can embed
the engine without learning that Windows exists.

## 2. The three pillars

### Pillar 1 — four-layer workspace split (#595)

```
rubash-core        lexer / parser / executor / builtins / usage / marker protocol
                   no terminal, no COM, no ConPTY, no git2.
                   The embeddable surface. Strictest semver.
rubash-driver      script_driver / run_stdin_script / invocation
                   non-interactive driving (#593/#314 pattern, generalized).
rubash-interactive readline / ConPTY / paste / themes / git2 / input translation
                   Windows-heavy, fast-iteration layer.
rubash (facade)    re-exports + bin. niubash depends ONLY on this.
```

- Groundwork: module dependencies are already one-directional; #570's
  contract tests pin the three invariants (native core / POSIX forms /
  verbatim fidelity); #597 removed the dead skeletons.
- Discipline: **coarse first** (3-4 crates, not 8). A cargo-metadata check in
  CI pins the dependency direction so nothing leaks back.
- Timeline: the mechanical split is 1-2 weeks on a long-lived branch with
  weekly rebases; fix-wave PRs keep landing on master during the split.

### Pillar 2 — the embeddable API (rubash-as-engine)

- **API RFC first** (#595 carries it). Any change to the pub surface of
  `rubash-core`/`rubash` after the split goes through an RFC — the pub face
  IS the contract face.
- Target surface (Session level, one layer above #593's driver level):
  input injection, output streams, lifecycle, event callbacks, rc policy hook.
- Consumers, in order: niubash (the reference host), oh-my-pi (#15582 —
  proposal pending our 1.5.0 data), a Zed extension PoC.
- Acceptance: a ~500-line "REPL inside an editor" demo that builds
  `rubash-core + rubash-driver` **without pulling ConPTY or Win32**.

### Pillar 3 — formalizing the engine/host boundary (the 846 blueprint)

The bridge audit found 846 `__RUBASH_*` environment-variable sites acting as
the de-facto engine/host interface: implicit, stringly, unversioned. After
the split, these are replaced family by family with **typed bridges** —
the history Provider pattern (#265) generalized to completion, events, and
rc policy. Every replaced family deletes host-side special-casing.

Precedents already landed: `rubash::usage` (#606 — the host/engine shared
help printer), `run_stdin_script` (#593 → niubash #314), and #359's plan A
(sidecar manifest), which demotes the user rc from "the product's second
database" back to a plain user file with management state in an explicit
interface.

## 5. Execution risks

1. **Split × fix-wave coordination** is the biggest execution risk: the fix
   fleet is still landing repairs. The split runs on a long-lived branch with
   weekly rebases; during the split, the rubash pub surface is FROZEN
   (non-RFC pub changes rejected at review).
2. The three #570 invariants are the split's acceptance floor — each layer
   gets its own contract test.
3. 1.4.x user value does not wait for the split; the refactor never blocks
   the train.
4. Unix surface work must not regress the Windows-first product: the unix
   lane gains the interactive harness, not product decisions.

## 6. Debugger placement

#497's M0 design (merged) defers three decision points (DP1 DAP-first,
DP2 `--debug` flag, DP3 breakpoint granularity). 1.5.0's core split makes
the debugger a natural core consumer; M0 implementation is scheduled for
1.5.0 or 1.5.x once DP1-DP3 are chosen (§8 D3).
